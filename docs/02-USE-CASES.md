## 1. 범위와 표기

이 문서는 기능 목록이 아니라 **사용자의 목표, 정상 흐름, 대안 흐름, 실패 후 회복**을 정의합니다. 화면 ID는 [IA](03-IA.md), 구현 계약은 [TRD](04-TRD.md)에서 이어집니다.

### 공통 행위자

| 행위자 | 역할 |
|---|---|
| Parent | 사진을 허용하고 주간 기록을 검토·저장하는 주 사용자 |
| iOS Photos | 권한 상태와 접근 가능한 사진 자산 제공 |
| Weekkeep Curation | 기기 내 분석과 선택 생성 |
| Local Notifications | 주간 리마인더 예약·전달 |
| RevenueCat/App Store | 상품 조회, 구매, entitlement, 복원 |
| Analytics | 사진 데이터를 제외한 제품 행동 이벤트 수집 |

### 우선순위

- `P0`: 공개 출시를 위해 반드시 완결되어야 함
- `P1`: V1 품질에 중요하지만 제한된 fallback 허용
- `P2`: 후속 개선

## `UC-01` 첫 실행에서 가치를 이해한다

### 목표

사용자가 Photos 시스템 팝업을 보기 전에 무엇을 얻고 왜 사진 접근이 필요한지 이해합니다.

### 조건

- 우선순위: P0
- 트리거: Weekkeep 최초 실행
- 사전 조건: `hasCompletedOnboarding == false`
- 시작 화면: `SCR-ONB-01 Welcome`
- 종료: 권한 요청 시작 또는 앱 이탈

### 기본 흐름

1. Parent가 앱을 실행합니다.
2. Weekkeep은 ‘지난 7일의 사진을 최대 7장으로 남긴다’는 결과 예시를 보여줍니다.
3. 같은 화면에서 ‘사진은 기기에서 분석되고 외부로 전송되지 않는다’는 짧은 설명을 보여줍니다.
4. Parent가 `지난 7일 남기기`를 탭합니다.
5. Weekkeep이 Photos 시스템 권한 요청을 호출합니다.
6. `EVT-onboarding_started`를 1회 기록합니다.

### 대안/예외

- A1. Parent가 프라이버시 설명을 탭하면 짧은 상세 sheet를 열고 원래 화면으로 돌아옵니다.
- A2. 앱을 종료하면 온보딩 완료로 기록하지 않으며 다음 실행에 같은 화면을 보여줍니다.
- A3. 이전 설치 데이터상 권한이 이미 결정됐다면 시스템 팝업 없이 `UC-02`의 해당 분기로 이동합니다.

### 사후 조건

- CTA를 탭한 경우 권한 상태가 해석됩니다.
- 단순 화면 노출만으로 온보딩 완료 처리하지 않습니다.

### 수용 시나리오

```gherkin
Given Weekkeep을 처음 실행했고 사진 권한이 결정되지 않았을 때
When 사용자가 "지난 7일 남기기"를 누르면
Then 시스템 권한 팝업 전에 앱의 결과와 기기 내 처리 설명을 볼 수 있어야 한다
And 알림이나 결제 요청은 나타나지 않아야 한다
```

## `UC-02` 사진 전체 또는 일부 접근을 허용한다

### 목표

사용자가 선택한 접근 수준을 존중하면서 접근 가능한 사진으로 Weekkeep을 사용합니다.

### 조건

- 우선순위: P0
- 트리거: `UC-01`의 CTA 또는 Settings의 재확인
- 사전 조건: Photos API 호출 가능
- 종료 화면: `SCR-WK-02 Curation Progress` 또는 `SCR-WK-01 This Week`

### 기본 흐름 — 전체 접근

1. iOS가 Photos 권한 선택지를 표시합니다.
2. Parent가 전체 접근을 허용합니다.
3. Weekkeep은 상태를 `.authorized`로 해석합니다.
4. `EVT-photo_permission_resolved(status: full)`을 기록합니다.
5. 최초 실행이면 `UC-04` Welcome Week 분석을 시작합니다.

### 대안 흐름 — 제한 접근

1. Parent가 일부 사진 선택을 선택합니다.
2. Weekkeep은 상태를 `.limited`로 해석합니다.
3. 제한된 사진만 분석할 수 있음을 과장 없이 알립니다.
4. `사진 선택 관리` 진입점을 제공하되 전체 접근을 강요하지 않습니다.
5. 접근 가능한 사진이 있으면 그대로 `UC-04`를 시작합니다.
6. 이벤트는 `status: limited`만 포함하고 선택된 사진 수나 ID를 보내지 않습니다.

### 예외

- E1. 권한 콜백 중 앱이 background로 가면 foreground 복귀 시 현재 권한을 다시 조회합니다.
- E2. 제한 접근이지만 범위 내 접근 사진이 0장이면 `사진이 아직 없어요`와 `선택 관리`를 구분해 표시합니다.
- E3. `.restricted`는 사용자 선택으로 해제할 수 있다고 말하지 않고 기기 정책 상태임을 설명합니다.

### 사후 조건

- 허용 상태가 앱 UI에 반영됩니다.
- 원본이나 선택 자산 ID는 영구 로그/분석 이벤트로 전송되지 않습니다.

### 수용 시나리오

```gherkin
Given 사용자가 Photos 일부 접근만 허용했을 때
When 지난 7일에 접근 가능한 사진이 4장 있으면
Then Weekkeep은 4장만으로 분석을 진행해야 한다
And 전체 접근 없이는 사용할 수 없다고 막아서는 안 된다
```

## `UC-03` 거부된 사진 권한을 회복한다

### 목표

권한을 거부한 사용자가 막힌 이유와 회복 방법을 이해합니다.

### 조건

- 우선순위: P0
- 트리거: 권한 결과 `.denied` 또는 앱 실행 시 기존 거부 상태
- 화면: `SCR-WK-01 This Week / permissionDenied`

### 기본 흐름

1. Weekkeep은 일반 empty state가 아닌 권한 전용 상태를 표시합니다.
2. ‘Weekkeep이 주간 기록 초안을 만들려면 Photos 접근이 필요하다’고 설명합니다.
3. Parent가 `설정 열기`를 탭합니다.
4. iOS Settings의 Weekkeep 페이지로 이동합니다.
5. Parent가 접근을 허용하고 앱으로 돌아옵니다.
6. 앱이 foreground에서 권한을 재조회합니다.
7. 허용됐다면 `UC-04` 또는 `UC-05`로 이어집니다.

### 대안/예외

- A1. `나중에`를 탭하면 기능을 속이지 않고 같은 제한 상태를 유지합니다.
- E1. Settings 이동을 시스템이 허용하지 않으면 수동 경로 안내만 표시합니다.
- E2. `.restricted`면 `설정 열기` 대신 보호자/기기 정책 확인 안내를 표시합니다.

### 수용 시나리오

```gherkin
Given Photos 접근이 거부된 상태에서
When 사용자가 Settings에서 접근을 허용하고 앱으로 돌아오면
Then 앱 재시작 없이 현재 권한을 다시 읽고 만들기 흐름을 사용할 수 있어야 한다
```

## `UC-04` Welcome Week를 만든다

### 목표

설치 직후 과거 전체 보관함 설정 없이 최근 7일의 작은 결과를 경험합니다.

### 조건

- 우선순위: P0
- 트리거: 최초 Photos 접근 허용
- 사전 조건: Welcome Week 미저장, 접근 가능한 권한
- 날짜 범위: `analysisStartedAt - 7 days ... analysisStartedAt`
- 시작 화면: `SCR-WK-02 Curation Progress`
- 종료 화면: `SCR-WK-03 Weekly Review` 또는 적절한 empty/error state

### 기본 흐름

1. Weekkeep이 분석 시작 시각과 rolling 7일 범위를 고정합니다.
2. 범위 안의 접근 가능한 이미지 자산을 가져옵니다.
3. 스크린샷과 숨김 자산을 제외합니다.
4. 최대 100장까지 기기 내 분석합니다.
5. 근접 중복을 묶고 품질과 날짜 분포를 반영해 최대 14장을 순위화합니다.
6. 최대 7장을 초기 선택하고 나머지 최대 7장을 교체 후보로 둡니다.
7. `EVT-curation_completed`를 사진 식별자 없이 기록합니다.
8. `SCR-WK-03 Weekly Review`에 결과를 촬영 시간순으로 보여줍니다.

### 대안/예외

- A1. 유효 사진 1–6장: 실제 장수만 보여주고 다음 단계로 진행합니다.
- A2. 유효 사진 0장: 날짜 범위와 권한 상태에 맞는 empty state를 표시합니다.
- A3. 접근 자산이 100장 초과: 일자별 대표 샘플링 후 100장만 분석합니다.
- A4. 사용자가 취소: task를 취소하고 저장/무료 횟수를 변경하지 않은 채 `SCR-WK-01`로 돌아갑니다.
- E1. 일부 iCloud 사진 다운로드 실패: 성공한 자산이 있으면 부분 결과와 생략 수를 보여줍니다.
- E2. 전부 실패: `UC-12`의 재시도 경로로 이동합니다.

### 사후 조건

- 저장 전 큐레이션 초안이 메모리 또는 임시 저장소에 존재합니다.
- 과거 7일 밖의 자산은 결과에 없습니다.

### 수용 시나리오

```gherkin
Given 지난 7일에 유효 사진이 5장뿐일 때
When Welcome Week 분석이 끝나면
Then 검토 화면에는 5장만 보여야 한다
And 7장을 채우기 위해 더 오래된 사진을 포함하면 안 된다
```

## `UC-05` 반복 주간 기록을 시작한다

### 목표

Welcome Week 이후 매주 하나의 기록을 반복 생성합니다.

### 조건

- 우선순위: P0
- 트리거: This Week CTA 또는 알림 deep link
- 사전 조건: 온보딩 완료, 접근 가능한 Photos 권한
- 화면: `SCR-WK-01` → `SCR-WK-02`

### 기본 흐름

1. Weekkeep이 `weekStart >= regularCycleStartsAt`을 만족하면서 가장 최근에 끝난 월요일 00:00–일요일 23:59 범위와 `weekKey`를 계산합니다.
2. 해당 범위가 끝난 다음 월요일 00:00부터 일요일 23:59까지의 완료 창인지 확인합니다.
3. 이미 저장된 `weekKey`면 `저장됨` 상태를 보여주고 중복 분석을 자동 시작하지 않습니다.
4. 해당 범위에서 접근 가능한 적격 사진 수를 확인합니다. 0장이면 권한 범위에 맞는 `noEligiblePhotos`를 보여주고 결제를 요구하지 않습니다.
5. 사진이 1장 이상일 때만 무료 저장 수가 2 미만이거나 Plus가 활성 상태인지 확인합니다.
6. 생성 가능하면 완료된 캘린더 주 범위로 `UC-04`와 같은 foreground 분석 pipeline을 실행합니다.
7. 최대 7장의 초안을 `SCR-WK-03`에 보여줍니다.

### 대안/예외

- A1. 적격 사진 0장: limited면 사진 선택 관리, full이면 다시 확인을 보여주며 paywall은 열지 않습니다.
- A2. 적격 사진 1장 이상 + 무료 한도 도달 + Plus 비활성 확인: `UC-10` paywall로 이동합니다.
- A3. `regularCycleStartsAt`부터 시작하는 첫 전체 캘린더 주가 아직 끝나지 않음: 남은 날짜를 세지 않고 `다음 기록을 기다리고 있어요` 상태를 보여줍니다. Welcome Week와 겹치는 이전 완료 주는 제안하지 않습니다.
- A4. 사용자가 완료 창을 놓침: 새 주가 끝난 다음 월요일부터 가장 최근 완료 주 하나만 제안합니다. 밀린 주 수, streak 손실, 연속 백필을 표시하지 않습니다.
- A5. 월요일 20:30 이전 또는 알림을 놓친 뒤: 완료 창 안이라면 같은 대상을 언제든 시작할 수 있습니다. 알림 시각은 gate가 아닙니다.
- E1. 시간대가 바뀜: 저장된 `weekKey`와 날짜 범위를 기준으로 중복 여부를 재검증합니다.
- E2. 일요일 밤에 시작한 흐름이 다음 월요일 00:00을 지남: 이미 고정한 `weekKey`와 초안을 저장 또는 취소할 때까지 유지하며 화면 중간에 새 주로 바꾸지 않습니다.

### 사후 조건

- 정확히 하나의 대상 주차에 대한 초안이 생성되거나, 명확한 gate 상태가 표시됩니다.

### 수용 시나리오

```gherkin
Given 한 캘린더 주가 일요일 23:59에 끝났을 때
When 다음 월요일 00:00부터 일요일 23:59 사이에 This Week를 열면
Then 직전 월요일부터 일요일까지의 완료된 주만 대상으로 해야 한다
And 같은 weekKey가 이미 저장됐다면 새 기록을 만들지 않고 저장된 주를 보여줘야 한다
```

## `UC-06` 제안 사진을 확인하고 교체한다

### 목표

준비된 초안을 그대로 승인하거나 필요한 사진만 바꾸어, 처음부터 고르는 부담 없이 부모가 최종 통제권을 갖습니다.

### 조건

- 우선순위: P0
- 트리거: 큐레이션 완료
- 사전 조건: 1장 이상의 초기 선택
- 화면: `SCR-WK-03`, `SHEET-REP-01`, `SCR-WK-04`

### 기본 흐름

1. Parent가 기기가 준비한 최대 7장 grid와 날짜 범위를 확인합니다.
2. 결과가 마음에 들면 별도 선택 없이 `지난주 남기기`를 탭해 `UC-07`로 이동합니다.
3. 사진을 처음 탭하면 Weekkeep은 그 사진을 교체 대상으로 선택하고 `이 사진 바꾸기`를 표시합니다. viewer는 아직 열지 않습니다.
4. 선택된 같은 사진을 다시 탭하면 `SCR-WK-04` 전체 화면 viewer를 엽니다.
5. Parent가 viewer를 닫으면 마지막으로 보고 있던 사진이 grid의 선택 대상이 됩니다. swipe하지 않았다면 원래 사진 선택과 위치를 유지합니다.

### 대안/예외

- A1. 사진 교체: 선택된 사진의 `이 사진 바꾸기`를 탭하고, 아직 선택되지 않은 후보 한 장을 고릅니다. 검토 중에는 같은 grid 위치만 crossfade로 바뀌고 나머지 6장의 표시 위치는 유지됩니다. `EVT-photo_replaced`는 사진 ID 없이 기록합니다.
- A2. 후보 없음: `교체할 다른 후보가 없어요`를 표시하고 현재 결과를 유지합니다.
- A3. sheet 취소: 현재 결과를 그대로 유지합니다.
- A4. 제한 접근 관리 후 후보 변경: 초안을 무효화하고 재분석할지 사용자에게 알립니다.
- A5. VoiceOver: photo의 `크게 보기` 또는 `사진 교체` custom action을 실행해 선택→재탭 순서를 거치지 않고 각 결과로 직접 이동합니다.
- E1. 교체 후보 원본이 그 사이 삭제됨: 후보에서 제외하고 나머지를 유지합니다.

### 사후 조건

- 선택에는 같은 asset이 중복되지 않습니다.
- `replacementCount`가 로컬 초안에서 증가합니다.
- accept-as-is 경로는 검토 화면이 나타난 뒤 저장까지 primary CTA 한 번이면 완료됩니다.
- 활성 검토 시간은 foreground에서만 누적하며 목표 중앙값은 60초 이하입니다.

### 수용 시나리오

```gherkin
Given Weekly Review에 선택된 사진이 없을 때
When 두 번째 사진을 한 번 탭하면
Then 두 번째 사진이 선택되고 "이 사진 바꾸기"가 보여야 한다
And 전체 화면 viewer는 열리지 않아야 한다
When 선택된 두 번째 사진을 다시 탭하면
Then 두 번째 사진부터 전체 화면 viewer가 열려야 한다
```

```gherkin
Given 7장 선택과 4장 대체 후보가 있을 때
When 두 번째 사진을 후보 C로 교체하면
Then 나머지 6장은 변하지 않아야 한다
And 최종 선택에 같은 사진이 두 번 존재하면 안 된다
```

### 사후 조건

- 성공 시 Plus entitlement가 활성입니다.

## `UC-12` 분석·사진·저장 오류에서 회복한다

### 목표

개인 사진의 실제 상태와 iOS 제약으로 생기는 실패가 데이터 손상이나 막다른 화면으로 이어지지 않습니다.

### 조건

- 우선순위: P0
- 트리거: 자산 fetch, iCloud 요청, Vision 분석, 저장 중 오류

### 오류 분류와 행동

| 오류 | 사용자 메시지 방향 | 1차 행동 | 보존해야 할 상태 |
|---|---|---|---|
| Photos 권한 변경 | 접근 범위가 바뀌었어요 | 설정/재조회 | 저장 기록 |
| iCloud network unavailable | 일부 사진을 불러오지 못했어요 | 다시 시도/가능한 사진으로 계속 | 완료 분석 결과 |
| 자산 삭제 | 이 사진은 Photos에서 찾을 수 없어요 | 닫기 | album slot/주차 |
| 분석 취소 | 분석을 멈췄어요 | 다시 시작 | 날짜 범위 |
| Vision 단일 자산 실패 | 사용자에게 개별 기술 오류 미노출 | 해당 자산 제외 | 나머지 점수 |
| 저장 실패 | 아직 저장되지 않았어요 | 다시 시도 | 전체 초안 |
| 데이터 store 손상 | 기록을 열지 못했어요 | 진단/지원 | 원본 store 백업 가능성 |
| 메모리 pressure | 분석을 완료하지 못했어요 | 더 작은 batch로 재시도 | 날짜 범위 |

### 기본 회복 원칙

1. 단일 사진 실패는 전체 분석 실패로 승격하지 않습니다.
2. 전체 실패 시 사용자가 이해할 수 있는 원인 범주와 다음 행동을 제공합니다.
3. 재시도는 다른 날짜 범위나 다른 주차로 바꾸지 않습니다.
4. 실패 이벤트에도 사진 ID, 경로, 정확한 촬영 시각을 포함하지 않습니다.
5. 저장 성공이 확인되기 전에는 초안과 무료 횟수를 유지합니다.

### 수용 시나리오

```gherkin
Given 20장 중 iCloud 사진 3장을 내려받지 못했을 때
When 나머지 17장으로 7장 선택을 만들 수 있으면
Then 부분 실패를 알리고 검토를 계속할 수 있어야 한다
And 전체 작업을 처음부터 강제하면 안 된다
```

1. Parent가 Photos 접근 상태(full/limited/denied)를 확인합니다.
2. 필요하면 iOS Settings 또는 limited picker로 이동합니다.
3. 알림 허용 상태와 기본 시각을 확인합니다.
4. Plus 상태와 `구매 복원`을 확인합니다.
5. 데이터 저장 설명에서 현재 iPhone 로컬 저장, 앱 관리형 백업 없음, 앱 삭제·기기 변경 시 유실 가능성을 확인합니다.
6. 프라이버시 설명에서 기기 내 분석과 외부 전송 금지 범위를 읽습니다.
7. 지원, 약관, 버전 정보를 확인합니다.

### 대안/예외

- A1. 앱이 background에 있는 동안 권한이 바뀌면 foreground에서 즉시 반영합니다.
- A2. Plus 상태를 불러오지 못하면 마지막 확인 상태와 `확인 중`을 구분합니다.
- A3. 개인정보 URL이 오프라인이면 앱 내 핵심 요약은 계속 읽을 수 있습니다.

### 사후 조건

- 설정 열람만으로 권한 팝업이나 구매 sheet를 자동 실행하지 않습니다.
